# Как ИИ анализирует данные именно этой базы данных

Частый вопрос при знакомстве с проектом:
> *«Если модели уже готовы и экспортированы в ONNX, как они могут знать специфику конкретной базы данных — продукты МТС (KION, Автопросматриватель TicTok), сервисы и точные названия 22 инженерных команд?»*

Ответ: **модели не были взяты «из коробки» как абстрактный сторонний сервис**. Они были **специально обучены (Supervised Learning) на историческом датасете инцидентов этой системы**.

Ниже подробно разобран весь цикл: от таблиц базы данных до математического инференса.

---

## 1. Схема: от базы данных к прогнозу ИИ

```
┌───────────────────────────────────────────────────────────────┐
│               1. Исторические данные (База данных)            │
│  - Тексты: header, description, productName, scenarioName     │
│  - Метки: реальная команда решения (assignedGroupName)       │
│  - Параметры: priorityId, urgencyId, impactId, serviceType    │
└───────────────────────────────┬───────────────────────────────┘
                                │
                                ▼
┌───────────────────────────────────────────────────────────────┐
│               2. Пайплайн обучения (ml/train_and_export.py)   │
│  - Построение словаря терминов МТС (TF-IDF N-grams)           │
│  - Обучение матриц весов связей: «Слова» ➔ «Команда»          │
│  - Калибровка вероятностной модели риска эскалации            │
└───────────────────────────────┬───────────────────────────────┘
                                │
                                ▼
┌───────────────────────────────────────────────────────────────┐
│               3. Экспорт в стандарт ONNX и JSON               │
│  - backend/models_ai/routing_hint.onnx                        │
│  - backend/models_ai/risk_assessment.onnx                     │
└───────────────────────────────┬───────────────────────────────┘
                                │
                                ▼
┌───────────────────────────────────────────────────────────────┐
│               4. Инференс в реальном времени (Go Backend)     │
│  - При поступлении нового инцидента в PostgreSQL              │
│  - Go применяет выученную матрицу весов к полям инцидента     │
│  - Выдает точную команду (e.g. «КЦ ДОИ VMWare» 97.8%)        │
└───────────────────────────────────────────────────────────────┘
```

## 2. Пошаговый механизм: как модель «учит» данные БД

### Шаг 1. Формирование обучающей выборки из БД
Каждый исторический инцидент в базе данных — это готовый обучающий пример:
* **Признаки (Features):** 
  $$\text{Текст} = \text{productName} + \text{service} + \text{scenarioName} + \text{header} + \text{description}$$
  *(Пример: «Автопросматриватель TicTok Экран-зеркало Подсветка Отказ Подсветка...»)*
* **Целевой класс (Ground Truth Label):** Поле `assignedGroupName`.
  В датасете представлено **22 уникальные команды** МТС:
  * *КЦ ДОИ Администрирование SAN*
  * *КЦ ДОИ VMWare*
  * *КЦ ИТ Media L2 KION*
  * *КЦ ИТ Active Directory*
  * *ОГЭ Приморье*
  * *КЦ ИТ Allure TestOps Support*
  * *(и еще 16 команд)*

### Шаг 2. Векторизация и словарь доменных терминов
Модуль `TfidfVectorizer` анализирует все тексты инцидентов и составляет частотный словарь технических терминов ландшафта МТС. 
Каждому слову присваивается вес важности (IDF). 

Если в тексте встречаются специфические маркеры (например, *«дисковый массив»*, *«LUN»*, *«SAN»*), модель связывает их с командой *«КЦ ДОИ Администрирование SAN»*, а слова *«стриминг»*, *«плеер»*, *«KION»* — с командой *«КЦ ИТ Media L2 KION»*.

### Шаг 3. Обучение классификатора (Supervised Training)
Модель логистической регрессии вычисляет матрицу весов $W$ размером $[22 \times N_{\text{слов}}]$.
Для каждой из 22 команд создается собственный математический профиль:
$$\text{Logit}_k = W_k \cdot \vec{x} + b_k$$
где $\vec{x}$ — вектор терминов входящей заявки, а $\text{Logit}_k$ — уверенность в назначении на команду $k$.

Через функцию **Softmax** логиты преобразуются в честные проценты вероятности:
$$P(\text{Команда}_k) = \frac{e^{\text{Logit}_k}}{\sum_{j=1}^{22} e^{\text{Logit}_j}}$$

### Шаг 4. Встраивание в микросервис
После обучения в Python веса сохраняются в кроссплатформенный формат **ONNX** и компактный JSON (`backend/models_ai/`).
Микросервис на Go загружает эти веса при старте и производит вычисления матричных произведений **прямо в оперативной памяти за 0.1 мс**, не делая внешних сетевых вызовов.

## 3. Как модель обновляется при накоплении новых данных в БД (Continuous Learning)

Система не статична — она рассчитана на непрерывное обучение по мере работы координаторов:

1. **Сбор обратной связи (Feedback Loop):**
   * Когда инцидент падает координатору, ИИ предлагает команду.
   * Координатор либо нажимает кнопку «Передать», либо вручную меняет команду в модальном окне.
   * Итоговое верное назначение и статус решения сохраняются в PostgreSQL.
2. **Переобучение (Retraining):**
   * Скрипт `ml/train_and_export.py` может запускаться периодически (например, раз в сутки через cron или по триггеру в БД).
   * Скрипт делает `SELECT * FROM incidents WHERE state IN ('Завершен', 'Закрыт')`, дообучает модель на новых решенных кейсах и перезаписывает ONNX-файл.
   * Точность рекомендаций непрерывно растет вместе с базой знаний.

## 4. А как работают альтернативные подходы (LLM / Трансформеры / RAG)?

Если вместо легковесной ML-модели подключать большую нейросеть (LLM) или трансформер (RuBERT), есть три классических способа подружить их с базой данных:

| Метод | Как нейросеть узнает данные базы | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Текущий (ML + ONNX)** | Обучается прямо на колонках и текстах из БД. | Мгновенно (< 0.5 мс), 30 КБ памяти, не требует GPU и интернета. | Ищет точные слова и термины, не понимает абстрактные метафоры. |
| **RAG (Векторный поиск в PostgreSQL)** | Инциденты переводятся в эмбеддинги и сохраняются в таблицу с `pgvector`. При новом сбое база находит 3 похожих решенных инцидента через косинусное сходство. | Понимает синонимы, не требует переобучения весов модели. | Требует расширения `pgvector` в Postgres и энкодер эмбеддингов. |
| **Fine-Tuning (Дообучение LLM)** | Базовая модель (RuBERT / LLaMA) дообучается на датасете инцидентов компании. | Глубокое понимание контекста и опечаток. | Требует GPU, терабайты памяти, долго обучается. |
| **Few-Shot Prompting** | В промпт к LLM на лету динамически вставляется список команд и последние решенные инциденты из БД. | Быстро настраивается без обучения. | Задержка ответа 1–3 секунды, расходы на токены API, риск галлюцинаций. |

## Итог

Модели в нашем проекте — это **не сторонний черный ящик**, а математический слепок исторических связей между проблемами и командами из **вашего датасета**. Они знают команды МТС именно потому, что обучены на предоставленных атрибутах инцидентов.
